# 安全与对齐 `[进阶]`

Agent 安全比普通聊天机器人更复杂。

聊天机器人主要输出文本。Agent 会读数据、调用工具、改变外部系统、记住信息、跨步骤规划,甚至和多个 Agent 协作。

因此安全问题不只是“回答是否合适”,还包括:

- 是否泄露敏感数据。
- 是否执行未授权动作。
- 是否误用工具。
- 是否被外部内容诱导。
- 是否把错误信息写入记忆。
- 是否在不确定时仍然自信行动。

Agent 安全的核心不是写一句“请安全行事”,而是建立多层防线。

![安全与对齐分层](../assets/part5-safety-alignment-layers.svg)

本章会讲:

- Agent 安全要保护什么。
- 对齐、安全、护栏、权限之间的关系。
- 常见风险模型。
- 分层防线如何设计。
- 为什么安全边界必须由 runtime 执行。
- 如何评估安全能力。

## 对齐和安全的区别

对齐通常指让模型行为符合人类意图、价值和规范。

安全更偏工程控制:即使模型出错,系统也不应造成不可接受的损害。

对 Agent 来说,两者都重要:

- 模型应理解用户真实目标。
- 模型应拒绝不合适请求。
- 系统应限制工具权限。
- 高风险动作应确认。
- 敏感数据应隔离。
- 失败应可追踪和恢复。

对齐让模型更愿意做对事。安全让系统在模型没做对时也有边界。

## Agent 的风险面

Agent 风险来自多个面。

| 风险面 | 例子 |
| --- | --- |
| 输入 | 用户请求越权、模糊或恶意 |
| 上下文 | 外部文档含恶意指令 |
| 工具 | 参数错、权限过大、副作用不可逆 |
| 记忆 | 保存敏感或错误信息 |
| RAG | 引用过期、无权限或冲突资料 |
| 多 Agent | 信息跨角色泄露、责任不清 |
| 输出 | 错误建议、泄露、误导用户 |
| 运行时 | 缺少审计、回滚、速率限制 |

安全设计要覆盖整个链路。

## 威胁建模:先问资产和攻击者

做 Agent 安全时,不要一上来就写规则。先做威胁建模。

可以问五个问题:

1. 要保护什么资产?
2. 谁可能滥用或攻击系统?
3. 攻击者能控制哪些输入?
4. Agent 能访问哪些工具和数据?
5. 哪些失败会造成不可接受损害?

例如企业知识助手的资产包括内部文档、客户数据、员工信息、系统 prompt、工具凭证和长期记忆。攻击者可能是外部用户、低权限内部用户、被污染文档的作者,也可能是无意触发边界的正常用户。

威胁建模能帮助你决定优先级。没有写工具的公开问答助手,重点是事实正确和输出安全;有邮件、数据库和生产发布工具的 Agent,重点是权限、副作用、审计和人类确认。

一个简单威胁表:

| 资产 | 攻击路径 | 控制 |
| --- | --- | --- |
| 内部文档 | 诱导模型输出无权限片段 | 权限过滤、输出脱敏 |
| 客户 PII | 通过外部邮件工具带出 | 数据流策略、确认、DLP |
| 写工具 | Prompt Injection 触发提交 | 工具策略门、preview/confirm |
| 长期记忆 | 不可信内容写入偏好 | 记忆写入门、来源校验 |
| 系统规则 | 用户要求泄露或覆盖 | 指令层级、拒绝策略 |

安全不是抽象品质,而是围绕资产、攻击面和损害半径做设计。

## 风险分级

不是所有动作风险一样。

可以按副作用和敏感度分级:

| 等级 | 例子 | 控制 |
| --- | --- | --- |
| 低 | 总结公开文档 | 普通生成和引用校验 |
| 中 | 查询内部只读数据 | 权限过滤、日志、最小上下文 |
| 高 | 发送邮件、创建工单、修改配置 | preview、confirm、幂等、审计 |
| 极高 | 转账、删除数据、发布生产变更 | 人类审批、多重校验、回滚预案 |

风险等级决定是否需要确认、是否允许自动执行、是否需要人工审核。

## 最小权限

Agent 工具权限应按任务最小化。

不要把“用户可能需要的全部工具”一次性暴露给模型。

更好的做法:

- 按任务类型加载工具组。
- 按用户权限过滤。
- 按阶段暴露工具。
- 写工具默认隐藏。
- 高风险工具需要确认后才可调用。

最小权限降低误用和注入风险。

## 数据最小化

模型不需要看到所有数据。

例如处理报销问题时,模型可能只需要:

- 交通类型。
- 金额区间。
- 政策条款。
- 审批状态。

不一定需要:

- 身份证号。
- 完整银行卡。
- 私人地址。
- 无关邮件内容。

上下文工程应该主动脱敏和裁剪。

## 指令层级

Agent 上下文中有不同层级:

1. 系统和安全策略。
2. 开发者/应用规则。
3. 当前用户请求。
4. 工具观察。
5. RAG 证据。
6. 外部不可信内容。
7. 记忆和偏好。

外部资料不能越级成为指令。用户偏好不能覆盖安全策略。模型推断不能覆盖工具观察。

这些优先级要在 context builder 和 runtime 中体现。

## Runtime 是真正边界

Prompt 可以提醒模型,但不能作为唯一安全边界。

例如:

```text
不要在用户确认前发送邮件。
```

这句话有用,但不够。系统还应该在 `send_email` 前检查:

- 当前用户是否授权。
- 收件人是否可发送。
- 内容是否包含敏感信息。
- 是否已经展示 preview。
- 是否有用户确认。
- 是否有 idempotency key。

如果缺少确认,runtime 应拒绝调用,而不是相信模型不会犯错。

## Human-in-the-loop

人类确认适合高风险动作。

确认界面应展示:

- 将执行什么动作。
- 影响对象。
- 参数来源。
- 可能副作用。
- 是否可回滚。
- 模型依据。
- 用户可修改内容。

不要只弹一句“是否继续”。用户需要足够信息做决定。

## 安全和用户体验

安全不能变成无意义阻塞。

好的安全设计会按风险分级:

- 低风险自动完成。
- 中风险解释并继续。
- 高风险请求确认。
- 极高风险要求人工审批。
- 明确违规则拒绝并给安全替代方案。

如果所有动作都要求确认,用户会疲劳。确认疲劳会降低安全。

## 安全评估

安全评估要有专门样本。

包括:

- 越权请求。
- Prompt injection。
- 敏感数据诱导。
- 高风险工具误用。
- 冲突指令。
- 过期证据。
- 多 Agent 数据泄露。
- 记忆污染。

指标包括:

- 拒绝正确率。
- 误拒率。
- 未授权工具调用率。
- 敏感信息泄露率。
- 高风险动作确认率。
- 策略绕过率。

安全评估不能只靠正常任务集。

## 安全 trace

每次安全决策要记录:

- 检查了哪些策略。
- 输入分类结果。
- 数据分类。
- 工具风险等级。
- 是否需要确认。
- 用户是否确认。
- 拦截或放行原因。

安全事件没有 trace,就很难复盘和改进。

## 事故响应

再好的安全设计也要假设会失败。

Agent 系统需要事故响应机制:

- 快速禁用高风险工具。
- 回滚 prompt、模型、工具 schema 或策略版本。
- 撤销或补偿错误副作用。
- 查询受影响 trace。
- 删除或修正被污染记忆。
- 通知相关用户或管理员。
- 把事故样本加入安全 eval set。

尤其是有写工具的 Agent,必须提前知道“执行错了怎么办”。例如邮件已发送不能真正回滚,只能发送更正邮件;数据库误写可能需要事务回滚或人工修复;错误记忆需要从主存储、向量索引和缓存中删除。

安全能力不只是防止事故,也包括事故发生后的止损和学习。

## 常见误解

### 误解一:模型已经对齐,系统就安全

不够。对齐降低风险,但不能替代权限、确认、审计和护栏。

### 误解二:安全就是拒绝更多请求

不是。安全是按风险采取合适控制,包括澄清、脱敏、降级和确认。

### 误解三:内部工具默认可信

内部工具也可能返回过期、错误或敏感数据。仍要校验和最小化。

### 误解四:人类确认万能

确认必须信息充分,否则只是把风险甩给用户。

### 误解五:安全策略写在 prompt 里就够了

不够。关键策略要由 runtime 执行。

## 本章小结

Agent 安全需要分层设计。模型对齐、系统指令、上下文隔离、工具权限、数据最小化、人类确认、护栏、审计和事故响应要共同工作。风险要分级,不同风险用不同控制。Prompt 是重要提示,但真正的安全边界应由 runtime、权限系统和策略引擎执行。安全能力也要被评估和观测,不能只在设计文档中存在。

下一章会讲护栏 Guardrails。安全是总体目标,护栏是把策略落在输入、上下文、工具和输出各阶段的具体机制。
